# Agentic AI Telecom Operations Assistant

An end-to-end **Agentic AI telecom operations platform** that combines multiple AI frameworks and operational data sources to handle telecom support, network diagnostics, billing resolution, policy retrieval, and customer communication.

The system uses **LangGraph** as the central orchestration layer, **LlamaIndex** for document RAG and semantic SQL, **Google ADK + A2A** for remote specialist agents, **CrewAI** for final customer communication, **SQLite** for operational telecom data, and **Streamlit** as the user interface.

---

## Project Overview

Telecom support requests often require information from multiple sources.

A single customer request may involve:

- network tower information
- outage history
- network performance
- customer subscriptions
- billing accounts
- duplicate charges
- billing credits
- service-level policies
- roaming policies
- device and 5G documentation

This project solves that problem using a **multi-agent architecture**.

Instead of one LLM attempting to answer every request, a supervisor routes the request to specialized agents.

```text
User
  │
  ▼
Streamlit UI
  │
  ▼
LangGraph Supervisor
  │
  ├──────────────► Policy RAG
  │                  │
  │                  ▼
  │              LlamaIndex
  │
  ├──────────────► Network Analytics
  │                  │
  │                  ▼
  │              Semantic SQL
  │
  ├──────────────► Network Diagnostics ADK
  │                  │
  │                  ▼
  │             Google ADK + A2A
  │
  ├──────────────► Billing Resolution ADK
  │                  │
  │                  ▼
  │             Google ADK + A2A
  │
  └──────────────► CustomerCommsCrew
                     │
                     ▼
                    CrewAI
                     │
                     ▼
              Final Customer Response
```

# Key Features

## LangGraph Orchestration

LangGraph acts as the central supervisor.

It determines which specialist agent should process a customer request and supports multi-agent workflows.

Main graph nodes:

```text
supervisor
policy_rag
network_analytics
network_diagnostics_adk
billing_resolution_adk
customer_comms_crew
```

Each specialist returns its result to the supervisor.

The final customer-facing response is generated by `CustomerCommsCrew`.

---

## Policy RAG

Policy-related questions are answered using **LlamaIndex document retrieval**.

Supported policy documents include:

```text
sla_policy.txt
roaming_policy.txt
billing_disputes_policy.txt
network_outage_procedures.txt
5g_faq.txt
device_upgrade_policy.txt
```

Example query:

```text
What will data cost in Japan?
```

Example routing:

```text
User
  ↓
PolicyRAG
  ↓
CustomerCommsCrew
  ↓
Final Response
```

---

## Semantic SQL Network Analytics

Operational questions are answered using **LlamaIndex Semantic SQL**.

The system converts natural-language questions into database queries against the telecom SQLite database.

Example:

```text
Summarize the Southwest region.
```

Example result:

```text
Southwest Region

TX-512 - Austin Riverside
Status: OPERATIONAL

TX-208 - Dallas Uptown
Status: DEGRADED
```

The system correctly interprets telecom operational statuses:

```text
OPERATIONAL
= functioning normally

DEGRADED
= functioning with impaired performance

DEGRADED does not mean inactive.
```

# Google ADK Network Diagnostics Agent

The Network Diagnostics service runs as a remote **Google ADK A2A agent**.

Default port:

```text
8001
```

Available network tools include:

```text
check_tower_status
run_connectivity_diagnostics
get_regional_network_summary
```

Example query:

```text
Why am I experiencing repeated 5G session drops near tower TX-512?
```

The agent can evaluate:

- tower status
- latency
- packet loss
- signal strength
- throughput
- active incidents
- regional network condition

---

# Google ADK Billing Resolution Agent

The Billing Resolution service runs as another remote **Google ADK A2A agent**.

Default port:

```text
8002
```

Available billing tools include:

```text
lookup_billing_account
check_duplicate_charges
apply_billing_credit
```

Example:

```text
Does CUST-10002 have any duplicate charges?
```

The system detects duplicate billing records using both explicit duplicate flags and matching billing-period records.

---

# Billing Credit Rules

Billing credits include safety and approval logic.

```text
Credit <= $50
        ↓
APPLIED automatically
        ↓
Customer balance updated
```

```text
Credit > $50
        ↓
PENDING_APPROVAL
        ↓
Balance remains unchanged
```

The system also includes idempotency protection.

If the same applied credit is attempted again:

```text
ALREADY_APPLIED
```

This prevents duplicate credits from being issued.

Validated behavior:

```text
$25 first attempt
→ APPLIED

$25 repeated
→ ALREADY_APPLIED

$75
→ PENDING_APPROVAL
```

# CrewAI Customer Communication

The final customer-facing response is generated using **CrewAI**.

The crew contains two sequential agents.

```text
Communications Specialist
          ↓
Quality Reviewer
```

The Communications Specialist transforms technical specialist outputs into a customer-friendly answer.

The Quality Reviewer checks the response for:

- clarity
- professionalism
- consistency
- completeness

The reviewed response becomes the final Streamlit output.

# Multi-Agent Workflow

The architecture supports queries that require multiple specialist agents.

Example:

```text
We had a 6-hour outage in the Midwest.
Am I eligible for an SLA credit and what does policy say?
```

Expected workflow:

```text
NetworkAnalytics
       ↓
PolicyRAG
       ↓
CustomerCommsCrew
       ↓
FINISH
```

This demonstrates that the platform is not limited to single-agent routing.

# Agent Execution Trace

The Streamlit interface displays a structured execution trace.

Example:

```text
Step 1 — NetworkAnalytics

Step 2 — PolicyRAG

Step 3 — CustomerCommsCrew
```

Each trace entry contains:

```python
{
    "worker": "AgentName",
    "output": "Agent result"
}
```

This provides visibility into how the multi-agent system handled the request.

# Hugging Face Offline Mode

The embedding model is cached locally.

To avoid unnecessary network calls and SSL retries, set:

```powershell
$env:HF_HUB_OFFLINE="1"
$env:TRANSFORMERS_OFFLINE="1"
```

before starting Streamlit.

# Startup Optimization

The LlamaIndex and Hugging Face components are preloaded and cached when Streamlit starts.

Without preloading, the Semantic SQL module initially required approximately:

```text
75 seconds
```

to import and initialize.

After preloading:

```text
NetworkAnalytics IMPORT: 0.00s
PolicyRAG IMPORT: 0.00s
```

This significantly reduces customer-facing query latency.

# Streamlit Configuration

The project contains:

```text
.streamlit/config.toml
```

with file watching disabled.

```toml
[server]
fileWatcherType = "none"
```

This prevents Streamlit from repeatedly inspecting heavy machine-learning packages such as Transformers and avoids unnecessary `torchvision`-related watcher errors.

# Google ADK Experimental Warnings

When the A2A services start, Google ADK may display warnings similar to:

```text
[EXPERIMENTAL] ADK Implementation for A2A support...
```

These messages are warnings from the current Google ADK implementation.

They do not indicate that the network or billing services failed.

The A2A protocol itself continues to operate normally.
